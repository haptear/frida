## 1. 一句话结论

**改名只挡"人工清理"和"名单扫描"，挡不住"目标进程自省 + 完整性校验"。**
要真正压低可检测面，顺序是：**① 改名 → ② 换加载方式（无文件/无端口/无独立进程）→ ③ 换 hook 结构（或承认残留）**；
而**最省事的一条捷径是走 gadget 内嵌**——它连"自定义 SELinux type"这个类别都不产生。

## 3. 路线选型（按场景直接对号入座）

| 场景 | 选什么 | 为什么 |
|---|---|---|
| **允许内嵌 APK / 可改包重签** | **gadget** | 不调 `frida_selinux_patch_policy()`（3 个调用点里没有 gadget）→ 不注册自定义 type、不写内核策略、不打自定义标签；进程列表无独立进程、TCP 面无监听 |
| server 路线 + 需 spawn/zygote（`frida -f`） | **方案 B（改名）—— 默认** | 功能零代价。A 会删掉 `patch.c:41-53` 的 13 条 allow 规则（含 `execmem`/`shell_data_file`/`zygote_exec`）→ spawn/zygote 失效 |
| server 路线 + 仅 attach 且实测通过 | 方案 A | 唯一能同时消除三项 SELinux 指纹；但把可行性押在设备 sepolicy 上 |
| 需要对抗"完整性校验/内核观察/时序" | 用户态**做不到** | 见 §6 |

**三种 SELinux 检测模型的能力边界（别把 B 当万能解）**

| 检测模型 | B（改名） | A（删注入） | gadget |
|---|---|---|---|
| 名单式：`grep -a frida /sys/fs/selinux/policy` | ✅ 可绕 | ✅ | ✅ 天然无 |
| **白名单式：设备 policy 与 AOSP 基线 diff** | ❌ **无效** | ✅ | ✅ 天然无 |
| 内核审计：写 `/sys/fs/selinux/load` 留事件 | ❌ 保留 | ✅ 消除 | ✅ 天然无 |

## 4. 六条必须记住的结论（每条都用源码否决了一个常见误判）

1. **改名 ≠ 隐身**：agent 活在目标进程内，`maps` 必有 `memfd:…frida-agent-64.so`（`linux-host-session.vala:69` + `linjector.vala:94/253`）。
2. **cloak 是双刃**：payload 层 cloak 确实能骗过 App 的 `opendir/readdir`（`cloak.vala:257-284`），但代价是**在 libc .text 上开 6 个 inline hook**；且 raw `getdents64` 直穿。→ **改名优于遮蔽**。
3. **`.text` 干净 ≠ 没被 hook**：`ThreadCountCloaker` 改的是 `libart.so` 的 **GOT 导入槽**（`cloak.vala:62-82`），GOT 在 rw- 数据页，前两条判据都抓不到。→ **P3 去 Interceptor 只是换指纹，不是消失**。
4. **8/10 项可单侧完成**：端口/目录用启动参数（`server.vala:33-57`）、线程名/memfd 名/导出符号/抽象 socket/label 全在 server 侧；只有 D-Bus 名族与 `frida:rpc` 前缀需双侧同源重编译（且只有抓包可见）。
5. **SELinux policy 注入比端口更难洗**：`server-glue.c:64` → `patch.c:41-53` 注入 13 条规则 + 2 个自定义 type，重启前持续存在。B 的改动面是 **9 处**（策略侧 5 + 标签 4），**只改一侧 = 静默失败**（`setfilecon` 返 -1，`patch.c` 不检查返回值）。
6. **重编译 frida-core 有硬门槛**：`frida-core/meson.build:11-19` 要求 Vala 版本以 `-frida` 结尾（得先自编译 frida/vala）；`releng/env_android.py:176` 硬编码 **NDK r29**。而 frida-gum 是纯 C → 自建 gum agent 反而更轻。

## 5. 结构面检测的四条判据（防守方视角，也是我们的暴露面）

| 判据 | 能抓到什么 | 我们能否消除 |
|---|---|---|
| 内存 `.text` vs 磁盘字节 | inline hook（任何 Interceptor 用法） | 仅当不用 inline hook |
| 无名可执行映射（匿名 RX 页） | Gum trampoline / thunk 页（每批 7 页，`gumcodeallocator.c:144`） | 用户态做不到 |
| **GOT 槽 vs 导出符号** | GOT 劫持（cloak 的手法） | 仅当不改槽 |
| **GOT 页 vma flags 翻转** | `mprotect(rw)` 窗口（FULL RELRO 下必发生） | 仅当不改槽 |

## 6. 用户态"消不掉"的五类（写进报告，别自欺）

1. **外部视角的 `/proc/<pid>/maps`**：shell/root 从进程外读，进程内 hook 完全无效。
2. **GKI 下的内核隐藏**：LKM 签名与 GKI 符号约束基本堵死。
3. **直接发 `svc` 的检测器**：任何 libc 层 hook 都拦不住。
4. **`.text` 自完整性校验（CRC/pagmap/so 自校验）**：只能比它更早执行，而一旦 hook 就落到判据 ①。
5. **时序/崩溃栈**：`debuggerd` 由独立进程读 `/proc`，cloaker 拦不到；hook 引入的耗时分布可统计识别。
