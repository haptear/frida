# 魔改 Frida 方案（选型 / 施工 / 验收）

> 配套：`01-Frida指纹盘点.md`（全部指纹的文件:行 证据）
> 基线：frida-gum `e1f746fe` · frida-core `61708ddb`
> 适用：受权沙箱内的客户端抗检测加固验证。目标不是"让 Frida 变得不可检测"，而是**把可检测面压到只剩内核/时序层**，并清楚知道残留在哪。
>
> **本轮范围（用户已明确）**：**纯分析交付** —— 只产出指纹盘点、方案选型、patch 清单与脚本文本。
> **不调用任何模拟器（MuMu 等）、不做设备侧动态验证、不构建不部署。** §5 的施工门禁与 §6 的验收矩阵是给后续授权实测用的口径，本轮不执行；需实机确认的推断统一列在 §9。

## 0. 选型结论（先看这张表再决定投多少工）

| 路线 | 消除的指纹 | 构建门槛 | 维护成本 | 适用检测强度 |
|---|---|---|---|---|
| **P1 官方源码 patch** | 命名层全消 + 端口/目录（免编译）+ 抽象 socket + SELinux label | **NDK r29 + frida-vala（自编译）+ Go** | 高（每次升级 rebase vala/dbus 相关） | 档 0-1（名单扫描、maps 自省、端口扫描、`ps`） |
| **P2 自建 gum agent**（**推荐**） | 命名层 + 通信层 + 进程层全消（无 frida-server、无端口、无 D-Bus） | **仅 NDK + meson**（frida-gum 是纯 C，不需要 vala） | 中（只需同步 gum 版本） | 档 0-2（含 maps 清洗对抗、线程名随机） |
| **P3 结构面 + 内核面** | 追加 .text 完整性、匿名 RX 页 | P2 之上 + 内核/自定义 ROM | 极高 | 档 3 部分（时序/内核观察仍不可消） |

**决策依据（硬事实，非偏好）**：

1. `frida-core/meson.build:11-19` 要求 Vala 编译器版本以 **`-frida`** 结尾，否则直接 `error()` 拒绝配置。也就是改 core 之前，你得先自己用 Meson 编译 `github.com/frida/vala`。
2. `.github/workflows/ci.yml:16` 指定 **NDK r29**；`:15` 还需要 Go 工具链（`FRIDA_COMPILER_MOD`）。
3. `frida-gum` 是纯 C + Meson，**没有 vala 依赖**，且 `gum_init_embedded()`（`frida-gum/gum/gum.c:230`）与 `gum_script_backend_obtain_qjs()`（`gumscriptbackend.h:67`）就是"自己造一个 agent"的全部入口。

→ 结论：**要"过检测"，走 P2；只想"防人工清理"，P1 的免编译部分（`-l` / `-d` / 改名）就够了，别过度工程。**

### 0.1 SELinux 这条的**最终裁决**（我拍板，含理由）

| 场景 | 选什么 | 理由（均有源码依据） |
|---|---|---|
| **允许内嵌 APK** | **gadget 路线** —— A/B 都不需要 | `frida_selinux_patch_policy()` 全仓只有 3 个调用点：`server/server-glue.c:64`、`inject/inject-glue.c:14`、`tests/runner-glue.c:47`，**`lib/gadget/` 一个不占**；`lib/gadget/gadget-glue.c` 不含 `frida-selinux.h`；`lib/gadget/meson.build:72` 的 deps 无 `frida_selinux_dep`。gadget 的载荷是 APK 自带 native 库，走系统本来就允许的路径 → **不注册自定义 type、不写 `/sys/fs/selinux/load`** |
| **server 路线 + 需要 spawn/zygote（`frida -f`）** | **方案 B（改名），默认位** | A 会删掉 `patch.c:41-53` 全部 **13 条 allow 规则**，其中 `execmem`（:41）、`shell_data_file:dir search`（:45）、`zygote_exec:file execute`（:46）是 spawn-gating / zygote 注入的必需项。B 功能零代价 |
| **server 路线 + 仅 attach** | 方案 A（**待实测**后才可用） | A 才是"消除指纹类"而不是"换个名字"；但前提是 `relabelto` 与 `execmem` 两项实测通过（见 §9 #2 / #2b） |

> 我最初把 A 定为"首选"，**这个判断被证据修正了**：A 的代价不是"少一次内核写"，而是**丢掉 spawn/zygote 能力**。现裁决 A 降为 `待实测条件选项`，B 为默认，gadget 为结构性最优。

## 1. 关键的"单侧 vs 双侧"兼容矩阵（决定工作量的一半）

官方 host（`frida` CLI / `frida-python`）与 server/agent 之间有协议耦合。**改动是否需要同步重编译 host，差别是"一天"和"一周"**。

| 改动项 | 需同步 host？ | 原因 |
|---|---|---|
| 线程名（`gum-js-loop` 等） | ❌ 否 | 纯内部命名 |
| agent 资源名 / memfd 名（`frida-agent-64.so`） | ❌ 否 | 注入端与 agent 同在 server 包内 |
| 导出符号 `frida_agent_main` | ❌ 否 | dlsym 双方都在 server 侧（`agent-container.vala:33` + `lib/agent/meson.build:39`） |
| 抽象 socket `/frida-<uuid>` | ❌ 否 | helper 自建自连（`frida-helper-process.vala:341-345`） |
| helper nice-name `re.frida.helper` | ❌ 否 | 仅进程显示名 |
| **端口 27042 / 目录 `re.frida.server`** | ❌ 否 | **启动参数即可**：`server.vala:33-57` 的 `-l/-d/--token/--certificate` |
| SELinux label 字面量 | ❌ 否 | 纯本地 |
| **D-Bus 名族 `re.frida.*17`** | ✅ **是** | host 与 server 通过 D-Bus 通信（`lib/base/session.vala` 13 处） |
| **`frida:rpc` 前缀** | ✅ **是** | agent JS ↔ host 控制器协议（`gumjs/runtime/message-dispatcher.js:24`） |

> **工程含义**：P1 里 **8/10 项可以单侧完成**。只有 D-Bus 名族与 `frida:rpc` 前缀需要双侧同源重编译——而这两项**只在抓包/流量审计可见**。若威胁模型里没有中间人抓包，这两项可以不动，P1 的实际成本立刻降为"一次 frida-server 重编译"。

## 2. 路线 P1：官方源码 patch 清单

> 每项都给出 文件:行。`★` = 优先级最高（目标进程内必现）。改法给"最小可用"，不强求优雅。

### 2.0 设计铁律：**改名优于遮蔽**（反直觉，但有源码依据）

直觉是"让 Frida 把自己藏起来"。源码告诉你相反：

- Frida 的自隐藏（`lib/payload/cloak.vala:237-284`）本身就是在 **libc .text 上开 6 个 inline hook**（`opendir/closedir/readdir/readdir64/readdir_r/readdir64_r`）。
- 于是你为了藏匿，反而多出 6 处**不需要任何 `frida` 字样就能抓出**的结构层证据（§01 §3.2 的 4/8/16 字节 redirect）。
- 而且它只挡 libc 路径，raw `getdents64` 直穿。
- 更隐蔽的一层：`ThreadCountCloaker`（`lib/payload/cloak.vala:62-82`）**不改代码**，而是把 `libart.so` 的 **GOT 导入槽**（`art::GetOsThreadStat`、`read`）改成指向自己的函数。GOT 在 **rw- 数据页**，所以 `.text` 比对和匿名 RX 页两条判据都抓不到它——**这说明"无代码改写的 hook"是可行的，P3 去 Interceptor 并不等于消失，而是换指纹**。

**所以正确顺序是：先把所有名字改成中性/随机 → 再用 `agent.vala:1123-1125` 把 3 个 Cloaker 彻底关掉 → 净减少 6 个 libc hook，而可检测字符面为零。**

### 2.2.1 SELinux 两套 patch 的**静态校验结果**（已做，非推断）

`_stealth/patches/` 下两套 patch 已在**钉定的 submodule commit 上做 `git apply --check`**（纯静态校验，无构建、无设备）：

| patch | 触及文件 | `git apply --check` |
|---|---|---|
| `selinux-A-remove-policy-injection.patch` | `server/server-glue.c`、`inject/inject-glue.c`、`lib/selinux/patch.c`、`lib/selinux/meson.build`、`meson.build`、`src/linux/linjector.vala`、`lib/pipe/pipe.vala` | ✅ 6 个 hunk 全通过 |
| `selinux-B-rename-types.patch` | 仅 `lib/selinux/patch.c`（策略侧 5 处） | ✅ 通过 |
| `selinux-B2-label-sites.patch` | `src/linux/linjector.vala` ×3 + `lib/pipe/pipe.vala` ×1（标签侧 4 处） | ✅ 通过（单独可打；B+B2 顺序打完后 `sysd_*` 命中 **9**、`frida_*` 命中 **0**，端到端静态验证过） |

**A 的语义**：删掉两处 `frida_selinux_patch_policy()` 调用，并把 **4 个打标点全部映射到已存在 type `app_data_file`**（`linjector.vala:268/275/281` + `pipe.vala:172`）——即 §2.1 #10 的"方案 A"完整实现，无遗漏点。

> 仍未验证（§9 #2）：root 域对 `app_data_file` 执行 `setfilecon` 的 `relabelto` 是否被 sepolicy 允许。**这是 A 能不能用的唯一开关**，B 是可用的回退。
> 所有权约定：A 作为**整体**由风险-2 维护（因为它必须原子），风险3 只复核不改 —— 避免同一批字符串两边同时改造成冲突。

> **裁决更新（本轮）**：A 的完整语义是"删掉 13 条 allow 规则 + 4 处打标改 `app_data_file`"，因此 **A 只适用于 attach-only**；需要 `frida -f`/spawn/zygote 的场景必须用 B。默认位已改为 **B**，A 挂 `待实测`。
> **B 的字符面精度**：`patch.c` 里是 **5 处** type 字面量（不是 6 处）：`"frida_file"` 3 次（`:42/:43/:85`）、`"frida_memfd"` 2 次（`:44/:92`）。此前"6 处"的口径有误，已更正。

> **B 的完整改动面是 9 处，不是 4 处**（这一条最容易踩）：`patches/selinux-B-rename-types.patch` 只覆盖 `patch.c` 的 **5 处**；另外 **4 处打标**（`linjector.vala:268/275/281` + `pipe.vala:172`）必须由注入侧同步改成**同名**。只改 4 处 label 而不改 `patch.c` → label 指向不存在的 type → `setfilecon` 返 -1 且**静默失败**。当前 B 选定的名字是 `sysd_file` / `sysd_memfd`（伪装成系统守护进程类型）。
>
> **名字策略要按威胁模型分**：
> - 名单式检测（`grep -a frida /sys/fs/selinux/policy`）：伪装名（`sysd_*`）即可绕过。
> - **白名单式检测**（把设备 policy 与 AOSP 基线比对，任何陌生 type 都算异常）：改名**无效**，只有方案 A（不定义 type）或 gadget 路线能过。这条决定了 B 的上限。
> **更强的结论**：`frida_selinux_patch_policy()` 的 3 个调用点里没有 gadget（见 §0.1 表）→ **gadget 路线天然不注入策略，A/B 都不需要**。

### 2.3 元数据与剥离

- **`frida-server` 二进制改名不需要改代码**：server 自身路径上 `prctl`/`set_prgname` 零命中（grep 只命中 `lib/base/linux-syscalls/*-glue.c` 的 syscall 表），进程名就是 basename（`comm` 前 15 字符）。改部署文件名即可。

## 3. 路线 P2（推荐）：自建 gum agent —— 无 server / 无端口 / 无 D-Bus

### 3.1 为什么这条路从根本上更干净

官方 frida 在目标进程里的可检测特征，**一半来自 frida-core 而不是 gum**：

| 特征 | 来自 | P2 是否还存在 |
|---|---|---|
| `frida-server` 进程 | core | ❌ 不存在（没有 server 进程） |
| 27042/27052 监听、D-Bus 握手 | core | ❌ 不存在（自有 transport） |
| 抽象 socket `@/frida-<uuid>` | core | ❌ 不存在（自有通道，名字自定义） |
| helper 进程 `re.frida.helper` | core | ❌ 不存在（注入方式自选） |
| agent memfd 名 `frida-agent-64.so` | core | ⚠️ 存在，但名字由你定（可随机） |
| `gum-js-loop` 线程名 | **gum** | ⚠️ 存在 → 单行源码改 |
| `.text` 改写 / 匿名 RX thunk 页 | **gum** | ⚠️ 存在（Interceptor 固有，见 P3） |
| `frida:rpc` 字面量 | **gum**（JS 资源） | ⚠️ 存在 → 改 JS 前缀（P2 下**无需要兼容官方 host**，改起来零成本） |

**P2 的核心收益**：`frida:rpc` 与 transport 全部归你，不再有"双侧兼容"约束；P1 里最贵的两项（#11/#12）直接消失。

### 3.2 架构

```

 ┌────────────┐   unix socket      ┌──────────────────────────────┐

 └────────────┘  (或 stdio / pipe) │  gum_init_embedded()         │
                                   │  gum_script_backend_obtain_qjs()
                                   │  gum_script_load_sync(js)    │

```

### 3.3 代码骨架（API 已核对头文件，可直接编译）

```c

#include <gum/gumscript.h>

}

int
main (int argc, char ** argv)
{

  GumScriptBackend * backend = gum_script_backend_obtain_qjs ();  /* gumscriptbackend.h:67 */

  GumScript * script = gum_script_backend_create_sync (
      backend, "agent", js_source, NULL, NULL, &err);    /* gumscriptbackend.h:76 */
  if (script == NULL) return 1;

  gum_script_set_message_handler (script, on_message, NULL, NULL); /* gumscript.h:66 */
  gum_script_load_sync (script, NULL);                             /* gumscript.h:56 */

  /* 自有主循环 + 自有线程名 */
  ...

```

**必须知道的坑（源码可证）**：

1. `gum_script_load_sync` 会创建 `gum-js-loop` 线程（`gumscriptscheduler.c:117`）→ 改名要在 gum 源码里做。
2. **Java bridge 不在 gum 里**：`grep -rln "Java.perform" frida-gum/bindings/gumjs/` 为空。17.x 的 `Java` 桥在 `frida-tools/bridges/java.js`，必须自己随 agent 下发并 `eval` 进脚本上下文，否则 `Java` 是 `undefined`。
3. 自建 agent 没有 `Script.runtime` 自动选择 → 显式用 QJS（`obtain_qjs`）或 V8（`obtain_v8`，体积大、特征多，不推荐）。

### 3.5 注入方式（决定②映射层还剩什么）

| 方式 | 前置条件 | maps 里留下什么 | 备注 |
|---|---|---|---|

## 4. 路线 P3：结构面与"做不到"清单

### 4.1 结构面（消除"无关键字"检测）

| 手段 | 可行性 | 说明 |
|---|---|---|
| 不再 inline hook native 代码 | 可行 | 改用 GOT/PLT 重定位、`dlopen` 参数拦截、数据面（配置/返回值）改写 |
| Java 层改走 `ArtMethod.entrypoint` 交换 | 可行 | 不触碰 ART 代码段，`libart.so` .text 与磁盘一致；但 entrypoint 指向的跳板仍是一段内存 → 需让跳板落在**已有可执行段**内（如 boot oat 附近的 code cave）或接受"anon RX 页"这条残留 |
| 去掉匿名 RX thunk 页 | **不可行（用户态）** | `guminterceptor-arm64.c:1394-1401` 的 thunk 页由 `gum_memory_allocate` 分配，无文件背书。要隐藏只能内核态 hook `mmap` 呈现 |
| 恢复 libc .text 干净 | 可行（推荐） | 关掉 3 个 Cloaker（`agent.vala:1123-1125`）即可消掉 6 个 hook；剩余只有你自己主动 hook 的目标 |
| 消除 `.text` 改写 | 仅当不做 inline hook | 检测法与对抗见 01 §5 |

### 4.2 明确做不到的（写进报告，不要吹）

1. **外部视角的 `/proc/<pid>/maps` 是终极不可欺骗的**：shell/root 从**进程外**读，目标进程内的 hook 完全无效。要挡这个只有内核（LKM/eBPF）。
2. **GKI（Android 13+ 主线内核）下 LKM 路线基本不可行**：内核模块签名与 GKI 符号约束会拦住绝大多数自定义 LKM。定制内核 + 解锁 bootloader 可行但已不属于"客户端加固验证"范畴。
3. **绕过 libc 直接发 `svc` 的检测器**：任何 libc 层 hook（`openat`/`read`/`fgets`）都拦不住。要么内联 patch 它的调用点，要么内核。
4. **自完整性校验（.text CRC + pagmap + so 自身校验）**：只能靠"比它更早执行 + hook 校验函数"，而一旦 hook 就有 ④ 层指纹 → 这是一个真正的死循环，只能降级到"改包静态 patch 掉校验"（那就变成另一个课题）。
5. **时序检测**：hook 引入的额外分支/缓存效应可被统计识别，无低成本对策。

> 一句话：**用户态魔改能把"名单式 + maps 自省 + 端口/进程扫描"全部清零，把"结构/完整性"压到需要专门比对才能发现，唯独"内核/外部观察/时序"无法消除。** 说清楚这条边界，比宣称"完全不可检测"更有价值。

> 下列每一步都需要设备 / root / 构建环境，属于本轮范围之外。放在这里是为了让后续实测有明确门禁与判定标准，而不是现在就去跑。

| 阶段 | 动作 | 通过条件（门禁） |
|---|---|---|

## 7. 维护与工程纪律

1. **patch 集化管理**：所有改动以 `git format-patch` 产出，放在 `_stealth/patches/`，按 `NNN-<指纹>.patch` 命名。升级 frida 时 `git am` rebase，冲突即"指纹点被改动"的告警。
2. **版本对齐**：host 与 device 侧必须同源同版本（P1 尤其；P2 无此约束——这是 P2 的隐藏收益）。
3. **自证悖论**：任何"我已经不可检测"的结论，必须有**至少两个独立来源**：外部 `/proc` 快照 + 静态 `.text` 比对（或第三方检测样本在干净进程里的结果）。
4. **一次只改一类**：命名层 / 通信层 / 结构层分开验证，否则失败无法归因（与 01 §1 的分层一一对应）。
5. **别为了过检测改坏功能**：每次改完跑一遍 Gate 2 的回归项；BTI/PAC landing pad、`-frida` vala 版本、符号脚本三处最容易踩。

## 8. 若你是防守方（同一份文档的反向用途）

魔改能力到此为止，反过来就是检测侧的加固建议，按性价比排序：

1. **把决策搬服务端**（唯一根治）：客户端只做"采集与呈现"，特权由服务端二次验签决定——技术上的对抗从此变成协议对抗，客户端魔改收益归零。
2. **外部进程观察**：不要在自己进程里自省（那一定能被 hook），由独立进程/守护进程读 `/proc/<target>/maps`、`/proc/net/*`、`ls -Z`。这是用户态最高性价比、且**无法被目标进程欺骗**的手段。
3. **结构性检测而非名单检测**：`.text` 与磁盘比对、匿名 RX 页、`ArtMethod.entrypoint` 合法性。改名字绕不过这三项。
4. **白名单式 ELF 校验**：按导出符号集合/段布局/大小指纹校验进程内每个 so，而不是匹配 `frida` 字样。
5. **别把检测放在 libc 层**：`open/read` 一把 hook 就废；检测逻辑放独立进程 + 直接 `svc`，或下沉内核（eBPF/LKM）。
6. **时序与行为**：hook 目标函数的调用分布、冷启动路径差异，作为兜底信号（成本高、误报要控）。
